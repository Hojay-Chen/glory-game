# 《廿四争锋》制作计划 v1（Production Plan）

> 建立于 2026-10-11。本文件是**制作层**的主计划：目标、质量门槛、阶段、分工与评审机制。
> 与它配套的：`docs/OPEN-ISSUES.md`（未决问题总表）、`docs/ux/ui-spec-v1.md`（界面规格）、
> `docs/art/art-bible-v1.md`（美术规格）、`docs/art/modeling-pipeline-decision.md`（建模管线）。

---

## 0. 先把话说清楚

**一晚做不出《守望先锋》。** 那是数百人年的工程量。本计划的目标不是"复制它的体量"，而是
**达到它的制作标准（production values）**——即：每一处玩家看得到、摸得到的东西，都经过
**明确的质量门槛**与**独立评审**，没有"先凑合"的占位残留。

**本次夜间窗口（用户睡觉期间）的可交付**：把"垂直切片"从**技术演示**提升为**可展示样品**
——界面有设计系统、角色有正经模型、场景有光照美术、有音效层次、经独立评审。

---

## 1. 产品定位

- **是什么**：3D 竞技场对战，**1v1 竞技**；复刻《全职高手》「荣耀」的**战斗机制**（24 职业 + 散人、
  技能取消、浮空连招、武器系统）。
- **不是什么**：不做养成/副本/经济/剧情/捏脸/外观商城。
- **体验支柱（Pillars）**——一切取舍以此为准：
  1. **读得懂**：不看名字只看画面，就能判断"谁、什么职业、什么状态、能不能打"。
  2. **打得爽**：每一次命中都有分量（顿帧、火花、数字、声音四层反馈齐备）。
  3. **值得看**：像电竞转播——构图、节奏、信息层次，旁观者也看得明白。
  4. **公平**：无随机、无局外成长；胜负只由操作与判断决定。

## 2. 质量门槛（Quality Bar）——"过关"的定义

> 这一节是本计划的核心。**任何交付物达不到对应门槛就不算完成**，不允许"先过、以后再说"。

### 2.1 界面（UI）
- [ ] **有设计系统**：颜色/字号/间距/圆角/动效时长全部来自一处 token，不散落魔数
- [ ] **层级清晰**：主信息（血量/技能 CD）在 0.5 秒内可读；次要信息不抢焦点
- [ ] **状态完备**：常态 / 悬停 / 按下 / 选中 / 禁用 / 冷却 六态齐全
- [ ] **动效克制**：所有过渡 ≤ 200ms 且有缓动，不用生硬线性；不做过场动画炫技
- [ ] **可访问**：正文 ≥ 16px；关键信息不只靠颜色区分（形状/图标冗余）；对比度 ≥ 4.5:1
- [ ] **无占位残留**：没有"TODO"、没有 Godot 默认控件外观、没有英文乱码

### 2.2 角色模型
- [ ] **剪影可辨识**：纯黑剪影下，阵营 100% 可辨、系别 ≥ 80% 可辨
- [ ] **比例正确**：头身比、四肢长度符合人体（不是"胶囊+盒子"）
- [ ] **拓扑干净**：四边面为主、无重叠面/法线翻转；命名规范
- [ ] **材质分层**：主色/暗部/金属件/自发光徽记分层清晰，非单色块
- [ ] **统一的制作基准**：所有角色共享一套比例与骨架规范

### 2.3 场景
- [ ] **光照有主次**：主光造型 + 补光读姿态 + 轮廓光抠边
- [ ] **材质有区分**：地面/墙体/掩体不同粗糙度，不是同一灰色
- [ ] **构图可读**：镜头能同时看清双方与地形关系

### 2.4 音效
- [ ] **四层反馈齐备**：命中/受击/技能/环境，且音量层次分明
- [ ] **有轻重**：大招与普攻听感明显不同
- [ ] 无爆音、无爆表（峰值 ≤ -1dBFS）

### 2.5 战斗可玩性（已有基础）
- [ ] 一场对局可完整打完并决出胜负
- [ ] 24 职业各自有可感知的差异
- [ ] 确定性不退化（现有 253 测试 + 三门禁全绿）

## 3. 阶段与交付物

| 阶段 | 交付物 | 状态 |
|------|--------|------|
| **P1 界面闭环** | 主菜单 → 选职业（含详情）→ 选武器 → 对战 HUD → 暂停 → 结算；设计系统 | 🔄 进行中 |
| **P2 角色建模** | 六系角色模型（Blender 制作 → GLB → 导入）；统一骨架与比例 | ⏸ 待 Blender 侧就绪 |
| **P3 场景美术** | 竞技场环境重塑（光照/材质/道具），不只是白盒 | ⏳ |
| **P4 音效** | 程序化基础音效（命中/受击/技能/UI）四层 | ⏳ |
| **P5 打磨与优化** | 动效、性能、（可选）骨骼动画 | ⏳ |
| **P6 独立评审** | 按 §2 门槛逐项 PASS/FAIL + 缺陷单 | 每阶段后 |

## 4. 分工与并行工作流

**制作与评审必须分离**（用户明确要求）：

| 角色 | 由谁承担 | 产出 |
|------|----------|------|
| 策划/规划 | 主 agent | 本文件、OPEN-ISSUES |
| 界面制作 | ui-programmer / godot-specialist agent | 屏幕与控件实现 |
| 界面评审 | **ux-designer + art-director（独立）** | 按 §2.1 逐项判定 |
| 角色建模 | 主 agent（经 Blender MCP） | .blend + .glb |
| 建模评审 | **art-director / technical-artist（独立）** | 按 §2.2 判定 |
| 场景美术 | technical-artist agent | 光照/材质 |
| 音效 | sound-designer agent（规格）+ 实现 | 音效规格与资产 |
| 代码质量 | lead-programmer（独立） | 代码评审 |
| 交付验收 | qa-lead（独立） | 验收报告 |

**并行原则**：互不写同一批文件的 agent 才并行；每完成一个阶段先过评审再进下一个。

## 5. 资产与管线

- **建模**：Blender 5.2.2（Windows）+ MCP for Blender → 导出 **GLB** → 导入 Godot
  （Godot 4.3 `gl_compatibility`；注意 draw call 比多边形更敏感）。
- **落点约定**：需要交给 Windows 主系统的产物放 `D:\luxera\<项目名>\`；
  项目内资产放 `src/Arena.Client/assets/`（Godot `res://assets/`）。
- **命名**：`<系别>_<部位>_<序号>`（见 art-bible §6）。
- **字体**：界面需内置 CJK 字体（OFL 许可），不依赖系统字体。

## 6. 风险

| 风险 | 影响 | 应对 |
|------|------|------|
| Blender 未开 / MCP 断连 | 建模停摆 | 先做不依赖 Blender 的 UI/场景/音效；Blender 就绪后立刻接 |
| 无美术人力 | 模型达到"业界标准"很难 | 走**参数化 + 模块化**：统一骨架与比例，靠剪影与材质分层达标；不追求高模 |
| 一晚时间有限 | 做不完 | 按 §3 优先级，P1 必达，P2–P4 尽力，P5 视情况 |
| Windows-MCP 看不到桌面（ssh 在 session 0） | 桌面自动化受限 | 主链路是 Blender MCP（走 TCP，不受影响）；如需桌面操作再装计划任务版 |
